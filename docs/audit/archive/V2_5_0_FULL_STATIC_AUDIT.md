# v2.5.0-G 全维度静态审计问题清单

- 基线版本：`2.5.0-G`
- Android `versionCode`：`19`
- 审计方式：源码/资源静态检查、引用/配置交叉检查、生命周期与信号流追踪、音频全轨解码、Python 工具语法检查、干净解压复验准备。
- 状态：**审计报告；本清单中的发现没有在本轮修复。** 为便于交付，仅新增本报告和导航链接；游戏逻辑、配置与资源在本次独立审计期间冻结。
- 严重程度：`P1` = 引擎/核心玩法/发布门槛；`P2` = 可能影响玩家体验、数据可靠性或性能；`P3` = 一致性、维护性或待产品决策。
- 证据类型：`静态确认` = 可以由源码直接确认；`高置信待渲染确认` = 源码结构表明存在风险，仍需真实引擎画面；`运行时待验证` = 需要 Godot/Android 才能定论；`产品决策` = 行为本身可解释，但需要明确预期。

> 重要边界：没有 Godot 4.7.x 可执行文件、Android Export Templates、Android SDK/JDK 与设备连接工具，因此本报告不能声称发现了所有运行时问题，也不能把基础词法扫描当作 GDScript 语义编译。下文是当前可用工具和人工追踪发现的完整问题清单，不是“已证明零遗漏”。

## 一、发布与核心验收门槛

### A-01｜P1｜Godot 语义编译、场景/Shader 导入与主场景运行尚未执行

- **类型：**运行时待验证；发布门槛。
- **位置：**全项目；入口 `project.godot:12-14`、`scenes/main.tscn:1-6`。
- **发现：**当前可执行检查只覆盖 Python 语法、资源/字面路径契约、脚本空白、基础引号/括号平衡与部分源码约束；这不能检查 GDScript 名称解析、静态类型推断、引擎 API、节点生命周期、资源导入、Shader 编译或运行时错误。
- **影响：**仍可能存在仅在 Godot 导入/编译/运行时出现的错误。特别是本工程大量通过脚本动态创建节点、材质、MultiMesh 和 UI，静态路径扫描无法覆盖所有对象类型与属性组合。
- **统一修复/验收要求：**在匹配的 Godot 4.7.x 环境先运行 headless editor/import，再运行主场景；清理所有 parser/error/warning 中会导致功能异常的项，保存完整日志。

### A-02｜P1｜APK 未构建；发布签名和导出环境还未闭环

- **类型：**发布门槛；签名字段留空属于当前安全设计，不是源码错误。
- **位置：**`export_presets.cfg:12,28-35,64-69`；`docs/build/ANDROID_RELEASE_CHECKLIST.md:5-26`。
- **发现：**项目没有随本版本交付已构建 APK。发布 keystore、alias 用户名和密码为空；`gradle_build/min_sdk`、`gradle_build/target_sdk` 也未显式固定。导出预设只启用 `arm64-v8a`，明确不包含 `armeabi-v7a`、x86 与 x86_64。
- **影响：**在配置自己的签名资料前无法完成正式签名发布；若不固定 Godot/模板/SDK/JDK 版本，跨机器构建结果和安装兼容性还需要确认。32 位设备不在目标 ABI 覆盖范围内。
- **统一修复/验收要求：**选定目标设备与发行渠道，固定引擎、模板、JDK/SDK 和 API 级别；密钥只在本地/安全 CI 中配置，不打包进源码；分别导出 debug/release 并安装启动。确认只支持 64 位是否为明确产品决策。

### A-03｜P1｜完整障碍模式库尚无自动可解性证明

- **类型：**运行时待验证；核心玩法风险，不代表已经证明存在无解模式。
- **位置：**`entities/spawner.gd:32-63`；当前静态契约主要锁定 950m 特殊组合，并未遍历整个 `PATTERNS` 集合。
- **发现：**代码注释写明模式库保证始终存在可行路径，但目前没有覆盖所有模式、所有车道、DDA 间距、章节机制、速度范围、跳跃/滑铲状态、落地恢复和道具组合的完整状态空间检查器。
- **影响：**未来更改障碍定义、碰撞盒或角色动作时，可能引入“当前模式列表不再保证可解”的回归；仅检查单个 950m 序列不足以证明整体公平性。
- **统一修复/验收要求：**实现可重复种子 + 玩家动作状态模型的关卡可解性验证；至少遍历全部模式/随机排列/最高速度/章节机制边界，失败时输出 pattern ID、seed 和障碍时间线；再用引擎跑局核对模型与真实碰撞。

## 二、数据保存与任务系统

### A-04｜P2｜音量滑块每变化一步都会同步写存档

- **类型：**静态确认。
- **位置：**`ui/menus.gd:267-285`；`scenes/main.gd:180-184`；`systems/progress.gd:185-231`。
- **发现：**`HSlider.value_changed` 每次触发都会发出 `settings_changed`；Main 随即调用 `progress._save()`。拖动一个音量滑块时，可能连续执行临时文件写入、备份删除/重命名和主文件替换。
- **影响：**低速存储设备上可能产生 UI 拖动卡顿与过量同步 I/O；即使每次文件很小，拖动过程中也没有节流/提交边界。
- **统一修复/验收要求：**拖动时只即时应用音量，使用 debounce/拖动结束信号统一持久化；用低端设备统计写入次数与拖动帧时间。

### A-05｜P2｜存档写入失败的返回值被忽略

- **类型：**静态确认。
- **位置：**`systems/progress.gd:185-231`。
- **发现：**`_atomic_save()` 会返回 `bool`，失败时写 `push_error`，但 `_save()` 不读取结果、不发失败信号，也不让购买/领奖/设置变更调用方知道写入没有成功。调用方先修改内存数据/显示成功反馈，然后只依赖错误日志。
- **影响：**磁盘空间不足、权限或文件替换失败时，当前会话里的奖励/设置看似已经完成，重新启动后却可能回退到旧存档。当前路径有备份恢复逻辑，但缺少用户可见的保存失败状态。
- **统一修复/验收要求：**让保存函数返回成功状态或发信号；交易型操作在失败时回滚/重试，或至少显示持久化失败提示；用故障注入验证 tmp、bak、主文件三种情况。

### A-06｜P2｜存档签名只覆盖三个字段，无法发现其余字段的合法值篡改/损坏

- **类型：**静态确认；本地单机项目中属于损坏检测覆盖不足，不应将当前签名视为防作弊机制。
- **位置：**`systems/progress.gd:214-266`，尤其 `228-234`。
- **发现：**签名 payload 只有 `wallet`、`stats.best` 与 `stats.totalRuns`，而 `ownedSkins`、`currentSkin`、`recentRuns`、其他统计、任务进度、成就和设置不进入签名。类型/白名单规范化能拦一部分错误，但其他字段若变成另一个合法值，不会触发备份恢复。`best` 在签名 payload 中还转换为整数，未覆盖小数部分。
- **影响：**备份恢复的触发范围不完整；部分存档损坏会被静默规范化，而不是优先恢复备份。已知 XOR/MD5 结构也不适合作为对抗主动修改存档的安全边界。
- **统一修复/验收要求：**明确目标是“防意外损坏”还是“防篡改”；前者应校验完整序列化 payload 并增加 schema/version，后者不能把硬编码密钥的本地校验当作安全方案。测试修改每个 section、截断文件、合法类型改值和备份回退。

### A-07｜P2｜每日任务按 UTC 日期切换，而不是设备本地日期

- **类型：**静态确认；产品决策。
- **位置：**`systems/progress.gd:351-372`。
- **发现：**任务日期使用 `int(Time.get_unix_time_from_system() / 86400)`，这等同按 UTC epoch 天数分桶。不同本地时区的玩家不会在各自当地午夜刷新。
- **影响：**玩家看到的“每日任务”刷新时刻可能与当地日历不同；如果原设计希望统一全球 UTC 刷新，这本身可接受，但 UI/产品规则目前没有明确说明。
- **统一修复/验收要求：**先确定按 UTC 还是本地日期；如采用本地日期，需要处理时区变化、夏令时和设备时间回拨，并为任务日定义稳定 schema。

## 三、渲染、画面与性能

### A-08｜P2｜PostFX CanvasLayer 的层级高于 HUD 和所有菜单层

- **类型：**高置信静态问题，最终视觉效果需要真实引擎确认。
- **位置：**`fx/post_fx.gd:7-15`（`layer = 50`）；`ui/hud.gd:30-35`（layer 10）；`ui/menus.gd:28-35`（layer 20）；`fx/post_fx.gdshader:18-44`。
- **发现：**PostFX 以全屏 `ColorRect` 在 layer 50 绘制，顺序高于 HUD/menus。Shader 读取 `hint_screen_texture`，对采样画面做色差/色调/暗角/颗粒处理，并最终输出 alpha=1 的完整屏幕颜色。
- **影响：**如果后缓冲采样按该 CanvasLayer 顺序包含前面绘制的 UI，HUD、暂停/结算/设置面板也会一起被色差、暗角和颗粒处理，文字/按钮可能出现边缘彩色偏移或对比度下降。这与“游戏画面后处理、UI 保持清晰”的常见目标不一致。
- **统一修复/验收要求：**在引擎中截图核对主菜单、设置、暂停、复活和结算面板；若确认 UI 被处理，调整渲染顺序或把游戏场景/界面分层，验证屏幕纹理复制的实际顺序。

### A-09｜P2｜全屏后处理持续运行在所有状态，且每帧做多次采样与逐像素运算

- **类型：**静态确认计算路径；实际 GPU 开销待测。
- **位置：**`scenes/main.gd:131-133`；`fx/post_fx.gd:17-25`；`fx/post_fx.gdshader:18-44`。
- **发现：**Main 每次渲染 `_process()` 都调用 PostFX，未依据菜单/暂停/设置或设备等级暂停；Fragment shader 在每像素采样屏幕纹理三次，并额外执行色调、距离、hash 颗粒与正弦扫描线计算。即使普通游戏中色差很弱，`time_` 仍持续变化，颗粒逻辑仍在运行。
- **影响：**在高分辨率手机屏幕上，这是一条常驻的 full-screen GPU pass；低档设备即使已减少雨与速度线，仍要支付该 pass 成本。可能影响帧时间、发热和耗电，但没有设备 profiling 不能给出损失比例。
- **统一修复/验收要求：**对菜单/暂停/普通跑局/超频进行 GPU 时间基线；在没有动态效果需求的状态停更/停用 shader；比较减少采样/降内部分辨率/关闭颗粒前后的帧时间与主观画面质量。

### A-10｜P2｜设备性能分级不覆盖真正昂贵的渲染开关

- **类型：**静态确认策略范围；实际卡顿与温控影响待测。
- **位置：**`core/telemetry.gd:56-86`；`project.godot:41-49`；`world/world.gd:87-109`。
- **发现：**设备档位按总内存与 CPU 核数做首帧判断；低档只调整雨粒子、速度线和 glow，高档是 `pass`。移动渲染器仍固定启用 4x MSAA、1.0 3D scaling、实时方向阴影（`shadow_enabled = true`），且 PostFX 常驻；没有基于实测 frame time、GPU 能力或热降频的反馈调整。
- **影响：**CPU/内存较高但 GPU 较弱的设备可能被分到高档；热机数分钟之后的降频也无法由首帧档位反映。是否超预算目前未知，但现有分级策略不能保证帧时间稳定。
- **统一修复/验收要求：**在目标设备记录 CPU/GPU 帧时间、1% low、内存、温度/降频；用实测数据决定阴影距离、MSAA、全屏效果和粒子预算，而不是只按 RAM/核心数推断。

### A-11｜P2｜HDR 选项与 Android 目标平台不匹配

- **类型：**平台能力不匹配的高置信静态发现，实际设备仍需确认。
- **位置：**`ui/menus.gd:258-265`；`scenes/main.gd:388-393`；`core/config.gd:215-222`。
- **发现：**设置面板对所有设备显示“HDR 广色域（OLED）”，Main 直接调用 `DisplayServer.window_request_hdr_output()`，没有基于 `DisplayServer.FEATURE_HDR_OUTPUT` 的能力检查，也没有反馈是否真的生效。Godot 4.7 DisplayServer 文档列出的 HDR output 支持平台为 Linux Wayland、macOS、iOS、visionOS、Windows，未列 Android。
- **影响：**此工程的交付目标是 Android；当前选项很可能在主要目标平台无视觉效果，却会保存为开启状态，令用户误以为打开了 HDR。
- **统一修复/验收要求：**在目标 Android/Godot 版本确认能力；不支持时隐藏或禁用该选项，或者将其重定义为真正可跨设备工作的 SDR 画面调校，而不要将其标为 HDR 输出。
- **参考：**[Godot 4.7 DisplayServer 文档](https://docs.godotengine.org/en/4.7/classes/class_displayserver.html)（`FEATURE_HDR_OUTPUT` 平台列表及 `window_request_hdr_output` API）。

### A-12｜P2｜屏幕安全区与不同长宽比尚未有设备矩阵验证

- **类型：**运行时待验证。
- **位置：**`project.godot:24-31`（412×915、`canvas_items`、aspect `keep`、immersive mode 由导出预设开启）；`ui/hud.gd` HUD 锚点与边距；`ui/menus.gd` 面板最小尺寸。
- **发现：**布局主要按固定 412×915 视口和固定像素边距设计；源码未见对 `DisplayServer.get_display_safe_area()` / display cutout 的显式适配逻辑。
- **影响：**不同屏幕比例、挖孔/刘海、折叠屏、系统显示缩放或不同触控区域上，顶部 HUD、右上角暂停按钮、底部超频按钮和设置面板的安全间距可能不足。静态扫描不能证明所有机型都重叠，但也不能证明已适配。
- **统一修复/验收要求：**用 18:9、19.5:9、20:9、平板/折叠屏与带挖孔设备做截图矩阵；必要时应用安全区 inset 与 UI 缩放策略，并验证触控区域不会落在边缘手势冲突区。

## 四、音频、随机性与运行生命周期

### A-13｜P2｜启动时预载所有 9 首音乐的实际内存/启动成本尚未测量

- **类型：**性能权衡，运行时待验证，不是已证实缺陷。
- **位置：**`systems/audio.gd:9-27`。
- **发现：**全部章节音乐和 BOSS 曲通过常量 `preload()` 在资源使用前加载。此举可以消除首次换主题时的路径 `load()`，但把资源加载工作移向项目资源初始化阶段。
- **影响：**可能降低中途切曲的加载风险，也可能增加冷启动时间和常驻资源开销。OGG 保持压缩流并不等同于完全没有内存/解码开销。
- **统一修复/验收要求：**记录冷启动耗时、峰值/常驻内存与首次换章时的卡顿；再决定全部预载、首章预载+其余按需加载或后台渐进预载。

### A-14｜P2｜没有显式应用后台/前台恢复生命周期管理

- **类型：**运行时待验证。
- **位置：**`scenes/main.gd`、`systems/audio.gd`、`systems/input.gd`；扫描未发现 application focus/suspend/resume notification handler。
- **发现：**没有显式在 Android 切后台时清理活动触点/输入、暂停音频与模拟、记录运行状态或恢复时重建状态的统一入口。
- **影响：**实际表现取决于 Godot/Android 对后台进程、音频和帧推进的处理；可能出现回来后音乐状态与游戏状态不同步、旧手势残留、计时突变或被系统杀进程后丢失最近一次未保存的局内状态。当前不能断言这些表现一定发生。
- **统一修复/验收要求：**真机执行来电、通知栏、锁屏、切应用、音频焦点变化和被系统回收等场景；再根据实测补齐统一 lifecycle hook 与恢复策略。

### A-15｜P2｜性能遥测不能测量文档声称的完整物理耗时，也不是完整回放系统

- **类型：**静态确认能力差距。
- **位置：**`core/telemetry.gd:1-7,33-54,56-86`；`README.md:36,83-87`；`docs/REGRESSION_CHECKLIST.md:32`。
- **发现：**Telemetry 顶部注释声称指标包括“物理进程耗时”，实际 `report` 不包含 physics/process CPU 时间、1% low、帧时间分布、GPU 时间或热状态；设备分级也不消费实测帧时间。随机 seed 被记录，但没有输入动作序列/时间戳回放，因此 seed 只能重现随机流，在相同调用路径下帮助定位问题，不能独立重放完整对局。
- **影响：**出现卡顿或随机局碰撞问题时，现有数据不足以直接定位 CPU/GPU/物理瓶颈或复现玩家的真实动作时序。
- **统一修复/验收要求：**补齐每帧耗时分布与 CPU/物理样本；如确实需要精确复盘，定义输入事件日志（模拟帧序号+动作+seed），并给出 deterministic replay 的限制和验证。

### A-16｜P3｜HUD 开关重新开启时可能短暂显示旧遥测，FPS EMA 也不重置

- **类型：**静态确认的小问题。
- **位置：**`scenes/main.gd:185-187`；`ui/hud.gd:210-234`；`core/telemetry.gd:25-32,40-54`。
- **发现：**开启“显示 FPS”时先调用 `hud.set_perf_visible(true)`，后调用 `Telemetry.set_enabled(true)`。HUD 会立即读取先前的 `Telemetry.report`；Telemetry 只清 `_acc/_frames`，并不清 `report` 或 `_fps_ema`。
- **影响：**再次开启后的首个采样周期内可能先显示旧报告；之后 FPS 平滑值还会受到关闭之前的 EMA 影响。影响较小，不属于核心玩法故障。
- **统一修复/验收要求：**启用遥测时清空/标记旧报告、重置 EMA，或显示“采样中”直到新报告到达，并调整调用顺序。

## 五、配置一致性、代码清理与维护成本

### A-17｜P2｜存在多组未接入或重复定义的配置项，修改后不会按字面产生效果

- **类型：**静态确认。
- **位置：**`core/config.gd:52-58,129-161`；`world/world.gd:90-97,622`；`fx/effects.gd:36-65`；`scenes/main.gd:20-22,508-535`。
- **发现：**`RUNTIME.viewDistance`、`RUNTIME.bloomRadius`、`RUNTIME.bloomThreshold`、`WORLD.chunkLength`、`WORLD.rainCount`、`CAMERA.lookAt` 没有实际代码引用；`RUNTIME.fogDensity`、`bloomStrength` 的同名值在 `world/world.gd` 被硬编码；道路循环长度在 `world/world.gd:622` 与 `world/road_grid.gdshader` 中重复写为 `42.0`；雨量在 `fx/effects.gd:38` 固定设为 1200，另由 Telemetry 直接改值。`STORE_KEYS` 是旧存储键映射表，当前 `ConfigFile` 存档并不使用它。
- **影响：**开发者可能以为编辑 `Config` 就能改变视距、Bloom、雨粒子、道路段长或摄像机 look-at，但真实运行不会跟随；重复常量将来可能出现漂移。
- **统一修复/验收要求：**逐项决定删掉、接线或转为唯一常量；给运行时可调参数增加“配置值→实际属性”的契约检查，避免保留貌似可配置但不生效的字段。

### A-18｜P3｜存在无消费者/无行为的兼容接口和未使用信号

- **类型：**静态确认；低优先级清理。
- **位置：**`core/game.gd:13,212-223`；`systems/audio.gd:245-247`；`scenes/main.gd:369-374`。
- **发现：**`Game.gameover` 声明并发出，但仓库中无 `gameover.connect` 消费者；结算目前由 `state_changed` 路径负责。`AudioEngine.unlock()` 函数体只有 `pass`，仍在每次开局由 Main 调用。它们是残留接口/死代码，而非本轮已证实的游戏崩溃。
- **影响：**维护者容易误以为这些接口是必要状态流程；改结算或音频时可能同时维护两条看似有效但只有一条实际生效的路径。
- **统一修复/验收要求：**确定兼容 API 是否仍需保留；若删除，更新调用点与文档，并增加“事件仅有一个权威路径”的检查。

### A-19｜P3｜核心脚本仍然过大，职责边界会提高后续改动的回归风险

- **类型：**静态确认的维护性债务，不代表行数本身就是 bug。
- **位置：**`entities/spawner.gd` 约 891 行；`world/world.gd` 约 851 行；`entities/player.gd` 约 785 行；`scenes/main.gd` 约 540 行；`systems/progress.gd` 约 483 行；`ui/menus.gd` 约 461 行。
- **发现：**Spawner 同时负责 pattern 数据、随机生成、池管理、渲染组装和碰撞；World 包含环境、建筑、远景、交通、地标、章节切换；Player 同时负责物理、动作、动画和皮肤；Main 集中大量跨系统信号编排。
- **影响：**局部修改可能跨越多个职责区域；没有真正的 Godot 单元/场景测试时，越长的同步函数越难做可靠的局部验证。
- **统一修复/验收要求：**先完成引擎与真机回归，再按职责分割（例如 SpawnPatterns/ObstaclePool/CollisionResolver、WorldEnvironment/CityCycle、PlayerMovement/PlayerVisuals）；保持外部接口稳定，每次只拆一块并立即引擎验证。

### A-20｜P3｜README 的基线/功能归属存在版本文案漂移

- **类型：**静态确认。
- **位置：**`README.md:3-7,13-21,28-41`；`docs/README.md:17-22`。
- **发现：**当前头部标记为 v2.5.0-G，但同一段仍称“当前版本基于 v2.4.0-G”；多个本轮之前升级项继续以 v2.4.0-G 的“当前重点”形式混在一起。`docs/README.md` 的当前版本审计索引最初只列升级审计，不区分完整问题清单与历史修复记录（本文件现已添加为新清单导航项）。
- **影响：**新对话/维护者容易误判当前基线和哪些内容是本版新增、哪些是历史改动。
- **统一修复/验收要求：**最终统一修复批次中集中重写版本摘要，明确“本版新增”“此前保留功能”“历史记录”，并由版本脚本核对 `project.godot`、Android preset、README 与 changelog。

### A-21｜P3｜复活状态事件先于玩家复位发出

- **类型：**静态确认的顺序风险；是否出现可见问题需引擎确认。
- **位置：**`scenes/main.gd:438-455`。
- **发现：**`_accept_revive()` 先调用 `game.accept_revive()`；该方法发出 `state_changed("running")`，Main 的状态处理器会立即开放输入并显示 HUD；之后当前函数才调用 `player.reset()` / `player.apply_skin()` 并恢复滑板等状态。
- **影响：**当前信号回调同步执行且通常会在函数返回前完成复位，因此不能直接断言有玩家能观察到的竞态；但其生命周期契约与 `_start_run()` 的“先准备后发布状态”原则不一致，后续如果加入 deferred 回调或异步等待，可能重新引入状态半初始化窗口。
- **统一修复/验收要求：**复活同样按“先清障碍、复位玩家/道具/音频、设置无敌时间，再发布 running”的顺序统一；测试连续点击复活、复活同时输入与复活后动作状态。

## 六、构建、平台范围和持久数据的产品边界

### A-22｜P3｜默认不允许 Android 自动备份，进度迁移只能依赖现有本地文件

- **类型：**产品决策。
- **位置：**`export_presets.cfg:55`；`systems/progress.gd:9,36-41`。
- **发现：**Android `user_data_backup/allow=false`，存档只在 `user://nr2099_save.cfg`，没有云存档/账号迁移。
- **影响：**卸载、清除应用数据或更换设备后，玩家进度不能通过 Android 自动备份恢复。这可以是有意的隐私或产品选择，但应明确接受。
- **统一修复/验收要求：**决定保持“纯本地且不备份”还是提供用户导出/备份路径；若开启系统备份，先审核保存内容与签名/恢复兼容性。

### A-23｜P3｜仅提供 arm64 导出，设备覆盖需要在发布声明中明确

- **类型：**产品决策/设备兼容范围。
- **位置：**`export_presets.cfg:30-33`。
- **发现：**仅开启 `arm64-v8a`，其他 Android ABI 关闭。
- **影响：**只支持 64 位 ARM 的目标设备范围。对近年的大多数设备可能足够，但不能覆盖所有旧设备/模拟器。
- **统一修复/验收要求：**按目标用户设备决定是否保留 arm64-only；如果扩展 ABI，分别评估包体、导出模板和实际设备兼容性。

## 七、统一修复建议顺序

1. **先清 P1 门槛：**Godot 4.7.x 导入/编译/运行；APK debug 导出、签名方案、目标设备安装；建立全模式障碍可解性验证。
